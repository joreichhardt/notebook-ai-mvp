## F4-01 · Discovery can begin using an already-resolved key after disconnect

**Severity: medium; confirmed route-level authorization/revocation defect, not cross-user credential theft or queued generation.** Registered routes are reachable by the admitted connection owner. The impact is another credential-bearing model-discovery call and possibly continued discovery after user revocation; no document prompt is sent by `models()`.

Minimal ordering supported by the existing code:

1. Request A passes admission and loads its active owned connection (`router.py:112-116` or `:133-136`).
2. A awaits Bitwarden read; an already-fetched key can be held while the await finishes/schedules its continuation.
3. Concurrent disconnect B commits removal or `disconnected` after cleanup failure. Alternatively app admission is revoked. A's previously materialized row is not automatically refreshed.
4. A unconditionally constructs the adapter and begins `models()` using the cached key (`:118` or `:137`). Later RLS flush/commit failure cannot unsend this request. Deleting the Bitwarden item does not erase a key already in memory or itself revoke the external provider key.

The new **ordinary failing tests**, not xfails, are in `tests/security/disconnect_boundary/test_discovery_revalidation.py`. They invoke the real two async route bodies and `owned`, with an independent materialized-row snapshot and synthetic store/adapter. The store changes current status to disconnected while returning the value already read; both real route continuations still call `models` with observed status `disconnected`. This is a genuine behavior test of the missing revalidation seam, **not** a real HTTP/DB concurrency test. CSRF and settings are replaced solely to isolate the seam; authentication/CSRF/RLS correctness is not claimed from these tests. Initial-inactive controls stop before secret resolution, and the existing ExecutionService under the same boundary change denies before adapter construction.

### Exact minimal regression / fix acceptance proposal

- Keep the two new RED cases: after secret-read completion following a committed disconnect, `test` and `select_model` must make **zero** model-discovery calls and return a sanitized inactive/absent authorization error. Initial-inactive controls and ExecutionService control must remain green.
- Extend an authorized kube1 test with **two real restricted PostgreSQL sessions**, synthetic secret/model endpoints, and event barriers: A reads active row and pauses at return from secret read; B performs actual disconnect and commits (202 cleanup-pending and 204 delete variants); release A; assert zero discovery requests. Repeat with admission deletion. Do not use live Bitwarden or a provider.
- Route discovery through an owned, fresh-session execution boundary (add a guarded discovery operation, rather than reusing generation or inventing capabilities). Fresh actor/admission/owner/active lookup after secret resolution, polling/closure for stalled discovery, and fresh authorization before metadata publication. A `refresh` on a cached row alone is not a short-transaction lifecycle design.
- Commit inactive status in a short actor transaction before slow cleanup if the desired guarantee begins at accepted disconnect; perform cleanup outside that transaction and record its outcome safely. Define the exact linearization semantics and cancellation deadline. This is a proposal, **no code change authorized or made**.

## Open integration gates, not new vulnerability findings

1. **Job/purpose admission before model use is not wired.** ExecutionService knows actor/connection, not notebook membership, lease, job, source, workspace policy or profile. Its module docstring explicitly assigns these checks to the caller (`execution.py:1-6`). There are no application call sites of ExecutionService outside its definition in this baseline. A future model worker must bind durable job actor, check fresh current admission/editor/membership/lease/source + explicit purpose immediately before I/O, use only that actor's active connection, and recheck during execution/before publish. Removal of a workspace member should not globally disconnect their personal connection for unrelated notebooks.
2. **No WAITING model execution exists at head.** In this schema the waiting state is `queued`; current dispatch selects only NULL connection/profile and TextWorker rejects embedding. Legacy RLS coverage demonstrates denial at the DB seam, not embeddings or credential resolution after queueing. Do not manufacture a runnable model job by bypassing 0006 merely to claim end-to-end coverage.
3. **Cancellation is best effort, not revocation of bytes already sent.** ExecutionService's fresh post-read check and poll protect subsequent exposure and cancel cooperative upstream work, but are not atomic with external network dispatch. Another commit can land after a check; polling/scheduling has a window. `asyncio.to_thread` cancellation also does not kill a running Bitwarden SDK thread. No DB transaction is held across ExecutionService's provider stream; transport response/client close on cancellation (`adapter.py:78-105`). This does not prove the remote provider stopped billing/work or that deletion revoked OAuth externally. Discovery routes currently lack even this watcher (F4-01).
4. **No proof for future profile/model/policy/caller validation.** Matching provider in RLS is not sufficient for model/revision/dimension compatibility. Trusted actor issuance, job-to-service authorization, model-purpose checks, fresh membership revocation while a future provider call is stalled, and no fallback to uploader/owner/admin all need genuine integration tests once the seam exists.
5. **Not all revocation permutations covered.** Missing/changed connection ID/owner/provider/secret ref before resolution and between checks, admission deletion at secret return, and real HTTP disconnect versus both stream/embed cancellation should be explicit cases. Existing paused-stream test covers secret-ref replacement, and real DB synthetic embed covers admission/connection changes; these do not cover all operations or prove live provider cancellation.
