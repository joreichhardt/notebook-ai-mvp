# Personal model keys in Supabase Vault

Bitwarden remains the store for kube1 deployment secrets, including the Vault database server encryption key. Personal model API keys are stored only in Supabase Vault, never via the deployment reader. No existing personal model connection was registered in either kube1 Notebook stack at the read-only inventory check.

## Database boundary

`deploy/private-ops/provider-vault.sql` is an operator install, not an unconditional Alembic revision. Only the full application stack needs Vault. The supported kube1 test DB image provides `supabase_vault` 0.3.1 but does not preload it by default. This version needs `shared_preload_libraries=supabase_vault` and `vault.getkey_script` pointing to a trusted executable that supplies the protected persistent key directly to PostgreSQL. Extension availability alone does not prove encryption works. Never use a fresh generated key at each start.

Only the non-login function owner receives access to the Vault internals; the API database role may call only the narrow wrappers. The wrappers derive the binding from the verified user's transaction-local subject and the server-generated connection UUID. This is a defense behind the trusted application, not a way to authenticate arbitrary clients holding database credentials. Never expose the wrapper schema via PostgREST or give its role or connection credentials to browsers, workers, or administrators of the Notebook app. Application authorization must still check admission, connection ownership/status and provider purpose before each use.

## Rollout gates

1. Verify the database image digest and configure the persistent, DB-only encryption key. Stage it via the existing read-only Bitwarden path; do not mount the reader or combine the key with a database dump. Test restart and restore against a disposable copy. A missing or wrong key must fail closed.
2. Install only in the isolated upload-test database first. Run `deploy/tests/provider-vault-smoke.sql` against a disposable instance of the pinned image, using only fixture values, before installation. Verify the effective grants of the actual login and browser roles again after installation.
3. Deploy the API that uses the Vault wrappers. Keep `NOTEBOOK_PROVIDER_VAULT_ENABLED` false (the default) until the database checks pass. Creation, replacement and deletion share a DB transaction with the connection reference. The inference reader revalidates the active connection and its reference before reading. The former Bitwarden runtime settings cannot enable the Vault adapter. Verify that driver, PostgreSQL, and API do not log bind values, query results, or secret-bearing errors. Do not return a stored key via HTTP.
4. Verify two-user isolation, key replacement and deletion, protected restart and restore, then actual inference with one authorized personal key and source-citation revalidation in system Chrome. Stay private; leave the Login stack alone.

Current state: the SQL wrappers passed synthetic owner/read/delete and cross-user/ACL checks in a disposable, networkless instance on kube1. A separate fixture was stored as ciphertext and remained decryptable after restarting that instance with the same key. A custom-format dump restored into a second disposable database under the same server key also remained decryptable. Restore on a separate host with the separately staged key is still an operational rollout gate. The API now uses the wrappers for personal model calls, including a replacement endpoint that returns only metadata. The Connections UI submits replacements without displaying a stored key. The application HTTP routes passed creation, replacement, and deletion against real Vault in a disposable kube1 database, with two fixture actors, simulated authentication, and rejection of stale key references. A separate database check verified that decrypting with the wrong server key fails. Neither the wrappers nor the new API are deployed. No real provider calls or browser checks were made.
