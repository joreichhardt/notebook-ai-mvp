## Python API: `app.db.uploads`

All helpers require an existing **short transaction** and never commit, perform I/O, select an actor or grant roles.

```python
reserve_upload(session, notebook_id, *, idempotency_key, filename, sha256,
               byte_count, media_type, connection_id=None, index_profile_id=None,
               document_id=None, expected_version_id=None) -> UploadIntent
finalize_upload(session, intent_id) -> UploadResult
check_upload_admission(session, intent_id, token) -> bool

# Separate trusted Storage-capability session, NEVER notebook_app:
claim_upload_io(session, intent_id, *, lease_seconds=60) -> UploadWriteClaim | None
confirm_upload_io(session, intent_id, token, *, sha256, byte_count) -> bool
list_cleanup(session, *, limit=100) -> list[UUID]
claim_cleanup(session, intent_id, *, lease_seconds=60) -> CleanupClaim | None
finish_cleanup(session, intent_id, token) -> bool
```

Frozen return records:

- `UploadIntent`: `id,document_id,version_id,job_id,workspace_id,notebook_id: UUID`; `storage_key,state,filename,sha256,media_type: str`; `byte_count: int`.
- `UploadResult`: `document_id,version_id,job_id: UUID`.
- `UploadWriteClaim`: `intent_id,token: UUID`; `storage_key,sha256,media_type: str`; `byte_count: int`.
- `CleanupClaim`: `intent_id,token: UUID`; `storage_key: str`.

`UploadConflict(ValueError)` means conflicting immutable content/filename under the same actor+notebook idempotency key (B maps409). `UploadUnavailable(ValueError)` is an opaque absent/inaccessible/unconfirmed/expired intent/finalization failure. Unsupported non-null options/replacement parameters raise `ValueError('upload_options_unsupported')`; non-TXT/MD media raises `ValueError('upload_media_unsupported')`. No embedding/model compatibility is assumed. Constraint/RLS/invalid-lease failures can also raise SQLAlchemy `DBAPIError`/`IntegrityError`; rollback and sanitize, never return raw SQL exceptions. Commit guards enforce rollback safety even if a caller ignores a false finalization RPC.

Reservation uses verified transaction-local actor context, never a browser-supplied actor. IDs come from protected PostgreSQL defaults; exact generated key is `workspace/notebook/document/version/original`, never a user filename. Hash/media/bytes/display filename are immutable intent metadata. Actual stream/content validation remains B's responsibility. No visible source/version/runnable job exists before complete trusted Storage confirmation and renewed actor finalization.

Same request replays the same identity; expired/cleanup tombstones never issue another write key. Stored/finalized replays do not re-PUT. Finalized replay rechecks current permission/source and returns the same IDs. Concurrent finalizers re-read intent state **after** the notebook lock, not from a cached ORM/pre-lock row.

## Lifecycle, locks and crash recovery

`reserved -> stored -> finalized`; unfinished timeout/revocation/parent teardown or finalized source teardown/supersession leads to `cleanup_pending -> deleting -> cleaned`. `cleaned` means **one reconciliation cycle**, not permanent remote finality; it becomes discoverable again hourly. Tombstones/keys remain indefinitely pending a separately approved retention policy, with no cascading parent FK or key/identity reuse.

- Intent expiry15 minutes. Single-use write claim binds token/deadline; matching hash+bytes receipt requires unexpired intent/write lease. Finalization also requires an unexpired receipt lease unless already finalized. No expired writer takeover at the same object key.
- New finalization locks notebook, inserts document/version/job as notebook_app, then verifier locks ledger and checks renewed admission/editor role, receipt and exact source/current-version/content/key/job/actor/options correspondence. Verifier does **not** create application rows. Commit is atomic.
- Deferred guards reject upload-bound source/version/job commits unless intent is finalized and inserted identities/content match, even if RPC is omitted or its false result ignored. The guard resolves jobs by **version ID as well as job ID**: only the canonical job may attach to an upload-bound version. Own/foreign second jobs cannot overwrite its projection. Future retry/embedding jobs need a separately reviewed design; unbound legacy/manual records keep existing behavior.
- Worker `claim_job` now locks source before job; claim/update then projects status. `lock_job_for_publish` and `finish_job` lock/recheck current source before job/status, including clock/token. Insert chunks and finish LAST in the same transaction; false means rollback all chunks/status. Existing token/attempt/connection/admission RLS fencing remains. No DB transaction spans parsing/provider/Storage I/O.
- Teardown locks parent/source then ledger. I/O/reconciliation touches ledger only, never waits for parent/source. Expiry discovery uses bounded `FOR UPDATE SKIP LOCKED`; tests prove a skipped committing finalization never becomes cleanup, and a skipped expired reservation is rediscovered/claimable after lock release.
- Triggered cleanup covers notebook/workspace hard cascade, document soft/hard deletion/current-version changes and unfinished admission/member loss/demotion. Shared **finalized** originals are not deleted merely because their uploader loses admission. Cleanup tokens fence stale finish/reclaim attempts and cannot claim active finalized objects. Trigger changes roll back with their enclosing transaction.
- Crash before PUT, after PUT without receipt, after receipt without finalization, inside finalization, after commit before HTTP response, and during cleanup retains either replayable state or durably scheduled reconciliation. Baseline unbound manual fixture versions are not retroactively claimed as live Storage-managed objects.

```python
# actor_tx / io_tx below are SHORT transaction factories, not new A5 APIs.
# Only verified identity or durable trusted job actor may enter actor_tx.
with actor_tx(verified_actor_id) as db:
    intent = reserve_upload(db, notebook_id, idempotency_key=key,
                            filename=display_name, sha256=digest,
                            byte_count=size, media_type="text/plain")
# transaction COMMITTED, no request-scoped DB transaction kept during I/O
if intent.state not in ("stored", "finalized"):
    with io_tx() as db:
        claim = claim_upload_io(db, intent.id, lease_seconds=120)
    if claim is None:
        raise UploadUnavailable("upload_unavailable")  # NEVER re-PUT same claimed key
    with actor_tx(verified_actor_id) as db:
        admitted = check_upload_admission(db, intent.id, claim.token)
    if not admitted:
        raise UploadUnavailable("upload_unavailable")
    # Trusted private-bucket non-upsert PUT + bounded readback SHA/bytes HERE.
    # No DB transaction open. Abort ambiguous writes into reconciliation.
    with io_tx() as db:
        confirmed = confirm_upload_io(db, intent.id, claim.token,
                                      sha256=readback_digest, byte_count=readback_size)
    if not confirmed:
        raise UploadUnavailable("upload_unavailable")
# Stored/finalized replays skip I/O and go directly to renewed actor finalization.
with actor_tx(verified_actor_id) as db:
    result = finalize_upload(db, intent.id)
# COMMIT before HTTP202; actor-private job is now claimable.
```

Example is control-flow guidance, not a complete HTTP handler; strict byte validation and actual trusted write/readback are B-owned. `check_upload_admission` is a fresh checkpoint, not an atomic guarantee across a remote request. Cleanup service lists bounded IDs, claims exact persisted key/token, commits, performs bounded remote reconciliation, then records a fenced cycle. No immediate best-effort DELETE is treated as final completion.

### Proposed semantics / small persistence extension

Limits: **10 outstanding per actor+notebook;50 outstanding per notebook;2 active per actor globally across ALL notebooks/workspaces;4 active per notebook**. These are logical admitted work/valid DB leases, NOT proof of two/four physically executing remote requests. A crashed/stalled process can outlive its DB lease; trusted I/O cancellation/deadlines/quiescence remain indispensable.

Add protected ledger columns `job_state` (NULL or queued/running/succeeded/failed/cancelled), `job_attempts`, `job_lease_token`, `job_lease_expires_at`, and `work_cancelled` (default false). No provider/error/content fields or raw-job discovery. Fixed canonical job INSERT/UPDATE/DELETE trigger receives NEW/OLD, validates job/version/actor/notebook against the existing ledger, and mirrors only those fields. It queries ledger only; no cross-actor raw-job SELECT. Derived indexed predicates, not separate increment/decrement counters:

- Outstanding at a single sampled DB time T: noncancelled reserved/stored intent with intent expiry>T, OR noncancelled finalized queued/running job (including expired running lease). Terminal jobs and abandoned/revoked/deleted work do not count; expiration of a processing lease alone does NOT silently discard queued recovery obligations.
- Active at T: mirrored running job with lease expiry>T, **even when work_cancelled or source-cleanup state is set**. Retain this occupancy until explicit trusted terminal acknowledgement or expiry; deleting/revoking a source must not immediately permit replacement physical work while its previous lease is valid. Preserve mirror/token/deadline on job DELETE/cascade for that interval.
- Finalization converts one reserved/stored outstanding unit into one queued unit, never counts both. Idempotent replay consumes zero new units even at capacity. Reclaim replaces an expired lease, not a second outstanding unit. Backoff stays outstanding. Failed terminal work releases outstanding; retry is unsupported in this slice.
- Role/admission deletion/demotion and source/version/parent deletion mark `work_cancelled` through fixed existing hooks, including finalized nonterminal work; this must NOT change finalized originals to Storage cleanup merely on uploader revocation. Claim fails thereafter. Outstanding releases atomically; active remains until its deadline/terminal acknowledgement. No raw-job mutation by cleanup owner.
- Attempts5 with expired running lease needs an explicit bounded ledger-only retirement routine/branch in existing reconciliation: mark work_cancelled once expired and exhausted. Otherwise outstanding leaks forever. This retires logical processing only, **not the finalized original object**; member-safe failed status for a revoked actor remains a separately defined presentation issue, not a new privileged status write.

### Serialization: recommend one nonblocking transaction gate first

Per-actor then notebook locks look attractive but parent cascades/revocation span actors, while existing source/job locks and AFTER triggers already run before ledger access. Adding a **blocking** actor/global advisory lock inside a row trigger produces a real inversion: transaction A owns gate and waits for source; transaction B owns source and waits for gate. Do not implement that design.

Small initial alternative: one fixed, namespaced **transaction advisory gate** for all quota-affecting transactions. Use ONLY `pg_try_advisory_xact_lock(fixed_key)`; false raises a stable retryable error and requires the entire short transaction to roll back. No blocking advisory acquire and no caller-supplied lock keys. This globally serializes DB bookkeeping, not network/parsing: lower throughput and unrelated-scope transient retries are intentional trade-offs to avoid an unreviewed actor-lock orchestration framework. Collision can cause denial/retry, never over-admission. Bound transaction/statement/lock timeouts and jittered whole-transaction retries; no external side effects before successful reservation/claim commit.

**Supported-call lock order:** gate -> notebook/parent (when needed) -> document/source -> canonical job -> current version/status -> ledger. Finalization inserts new uncommitted rows rather than taking an existing job lock. Its verifier may touch ledger then read own rows under the already-held gate; SELECT reads do not add a reverse row-lock wait. For transactions spanning multiple objects, ascending UUID within each tier; parent cascade follows the gate, so it cannot race a cooperating claim. Membership/admission administrative mutations take gate before their own rows and before derived ledger changes. I/O-only routines: gate -> ledger, never parent/source/job.

All A5 entry helpers must attempt gate as their **first SQL operation**, before notebook/source locks: reserve, finalize/replay, claim, heartbeat, publish/finish, delete/revoke; cleanup/receipt routines also acquire gate before ledger mutation. `lock_job_for_publish` holds it through chunks+finish until commit. The job trigger mirror must run **after** the job's status-projection AFTER trigger (fixed trigger-name ordering), so job -> version -> ledger remains consistent; an initial BEFORE trigger validates transition/acquires-or-checks gate before projection. Reserve INSERT and relevant ledger mutations validate under the gate too. Triggers remain the authority, helpers are merely the low-contention path.

**Direct SQL fallback:** before any quota-changing row path or cascade can touch lower-tier rows/ledger, a fixed BEFORE trigger must try the gate. PostgreSQL may already hold its target row lock: on contention it raises immediately rather than waiting for gate; if it wins, no competing gated transaction exists. Thus direct allowed UPDATE cannot bypass quota or introduce a gate-wait cycle. Add guards to relevant ledger/job/source/parent/admission/member INSERT/UPDATE/DELETE paths, including cascades and TRUNCATE denial. A trigger installed only AFTER version/ledger writes is insufficient. Existing arbitrary multi-row SQL/SELECT FOR UPDATE can still deadlock outside this protocol: runtime remains trusted, PostgreSQL abort/timeouts are recovery, not a claim of universal deadlock-freedom. No generic SQL endpoint is allowed.

Run capacity reads as separate statements **after winning gate**, in VOLATILE routines under READ COMMITTED; reject other isolation levels for these entry points. A count taken from a snapshot before waiting/winning a lock is not valid. Tests must deliberately start both competing statements before either commits. Sample T once for both active predicates in one operation. Database time advancing only expires occupancy; heartbeat/reclaim is separately serialized and rechecks capacity if it would acquire a newly active slot.

### Direct job writes and A3 cooperative boundary

Counts must be enforced by fixed transition/mirror triggers, not `claim_job` Python. Otherwise a permitted raw `UPDATE status='running'` bypasses admission. Validate NEW against OLD under the gate, before projection/mirror publication:

| Transition | Required rule |
|---|---|
| Canonical INSERT | Exactly queued/attempts0/no lease; same ledger identity/options; finalization commit guard unchanged. |
| queued -> running | attempts=OLD+1<=5, available_at reached, current authorized source, fresh non-null token, bounded future deadline; proposed ledger active totals<=2/4. |
| expired running -> running | OLD deadline<=T, attempts+1<=5, different token, both capacity checks; replaces prior mirror atomically. |
| running heartbeat | Same token/attempts, OLD deadline>T, new deadline>=OLD and <=T+300s; cannot shorten/backdate to manufacture spare slots or revive expired token. |
| running -> terminal | Live lease and actor/source authorization rechecked; no lease fields, attempt count unchanged; release logical active/outstanding atomically with existing publication/status transaction. |
| terminal -> queued/running | Reject for upload-bound jobs in this first slice; explicit retry contract is future work. |
| deletion/cascade | Keep last live lease occupancy in ledger until expiry; retire outstanding, never delete the ledger key or re-admit the cancelled intent. |

Direct writes to version processing metadata never alter quota fields. Replacing canonical job IDs, second jobs, changing actor/scope/options, decreasing attempts, changing available_at to escape eligibility, shortening/clearing a running lease without terminal transition, and direct ledger mirror edits must fail. Existing runtime table-wide job UPDATE/INSERT grants allow all of these attempts to reach guards; they are not trustworthy merely because Python does not issue them.

**Honest limit:** a trusted notebook_app connection can still claim that an authorized running operation finished and submit a syntactically valid terminal UPDATE; DB has no proof that its external process stopped. NEW/OLD trigger enforcement preserves ledger/job consistency and numeric DB lease limits, not hostile-runtime physical execution accounting. Making claim/heartbeat/finish truly capability-only would require revoking existing raw mutation grants and replacing them with scoped routines (and possibly chunk publication capability)—a materially different authorization project, NOT silently part of this quota design. Main must choose whether the documented A3 trusted-cooperative boundary is retained.
